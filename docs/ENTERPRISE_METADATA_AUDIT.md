# Shipyard Enterprise Metadata Audit

**Audit date:** 2026-07-25
**Canonical site:** https://genshipyard.com
**Repository:** https://github.com/luch91/shipyard
**Scope:** Public metadata, discovery, AI compatibility, security metadata,
developer documentation, and machine-readable resources.

## Executive summary

Shipyard now has a coherent public metadata layer for search engines, social
platforms, browsers, feed readers, AI retrieval systems, and security
researchers. The implementation is additive and does not change application
business logic, UI rendering, wallet behavior, authentication, or data access.

The implementation follows Google Search Central guidance where Google defines
behavior, RFC 9116 for `security.txt`, RSS 2.0 for the product-update feed, the
Web App Manifest specification through Next.js metadata routes, and official
crawler guidance from OpenAI, Anthropic, and Perplexity.

`llms.txt` is treated as an emerging proposal, not a ranking standard.
`ai.txt` is explicitly labeled non-standard and informational. Neither file
overrides `robots.txt`, HTTP headers, page-level robots directives, terms, or
applicable law.

## Guardrails

- No business logic changed.
- No UI or visual application component changed.
- No authentication behavior changed.
- No Search Console token, rating, review, social handle, or ownership claim was
  invented.
- Private and personalized HTML routes use `noindex` metadata rather than
  relying on `robots.txt` as a privacy control.
- APIs receive `X-Robots-Tag: noindex, nofollow, nosnippet`.

## 1. robots.txt review

**Purpose:** Tell cooperative crawlers which URL paths may be requested and
advertise the canonical sitemap.

**Implementation:** The default group allows public pages and disallows `/api/`.
Explicit groups allow `OAI-SearchBot`, `PerplexityBot`, `ClaudeBot`, and the
existing `GPTBot` policy while also excluding `/api/`. The sitemap is declared
as `https://genshipyard.com/sitemap.xml`.

**Why it matters:** A clear policy avoids accidentally blocking crawlable
product content while reducing pointless API crawling. Robots rules are crawl
controls, not security or guaranteed de-indexing.

**AI impact:** OpenAI search, Perplexity, and Anthropic crawlers can retrieve
public pages. `GPTBot` remains allowed, preserving the repository's pre-existing
training-crawler policy. Allowing a user agent does not guarantee retrieval,
citation, ranking, or licensing.

**SEO impact:** Googlebot remains covered by the permissive default group.
Important CSS, JavaScript, icons, and metadata resources are not blocked.

**Browser impact:** None; browsers do not use robots directives for navigation.

**Maintenance notes:** Review whenever public/private route boundaries change.
Do not place secrets in robots.txt. If training policy changes, update training
crawler groups separately from search/retrieval crawlers.

Reference: [Google robots.txt guidance](https://developers.google.com/search/docs/crawling-indexing/robots/intro)

## 2. Sitemap validation

**Purpose:** Provide search engines with the canonical public URLs Shipyard
considers important.

**Implementation:** `/sitemap.xml` is generated by `app/sitemap.ts` and contains
only canonical HTTPS URLs for the home, deploy, templates, comparison, registry,
builders, skills, terms, and privacy pages.

**Why it matters:** A sitemap improves discovery and communicates the preferred
URL set without exposing personalized, administrative, handoff, API, or
parameterized URLs.

**AI impact:** Retrieval systems that consume sitemaps receive a concise list of
authoritative public entry points.

**SEO impact:** Sitemap URLs agree with page canonicals. `lastmod`,
`changefreq`, and `priority` are omitted because Shipyard does not currently
have trustworthy per-page modification timestamps; inaccurate values are worse
than no values.

**Browser impact:** The XML remains directly readable at `/sitemap.xml`.

**Maintenance notes:** Add a route only when it is public, canonical, returns
HTTP 200, and is intended for indexing. Submit this URL in Search Console after
deployment.

Reference: [Google sitemap guidance](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap)

## 3. llms.txt

**Purpose:** Offer a compact, high-signal map of Shipyard for systems that elect
to consume the emerging `llms.txt` format.

**Implementation:** `/llms.txt` describes Shipyard, the four selectable network
environments, Clarke's coming-soon status, core workflows, authoritative public
links, product facts, and external GenLayer references.

**Why it matters:** The file gives retrieval systems a stable summary that is
less noisy than a fully rendered application shell.

**AI impact:** It may improve machine comprehension for tools that voluntarily
support the proposal. No major crawler is assumed to consume it, and it creates
no ranking entitlement.

**SEO impact:** Neutral. Google does not document `llms.txt` as a ranking or
indexing directive.

**Browser impact:** Plain-text Markdown is readable without JavaScript.

**Maintenance notes:** Update network status, key routes, product claims, and
external references alongside product releases. Keep it concise and factual.

Reference: [llms.txt proposal](https://llmstxt.org/)

## 4. ai.txt

**Purpose:** Provide a graceful pointer to authoritative AI-oriented discovery
resources while clearly describing the file's status.

**Implementation:** `/ai.txt` labels itself informational and non-standard,
links to the canonical site, `llms.txt`, robots policy, sitemap, and source, and
states that it does not override established access controls or grant a license.

**Why it matters:** Some tools probe for `ai.txt`, but there is no adopted web
standard governing it. Explicit labeling prevents accidental
misrepresentation.

**AI impact:** Provides a useful directory only to systems that choose to read
it.

**SEO impact:** None expected; it is not a Google Search directive.

**Browser impact:** Plain text only.

**Maintenance notes:** Never place crawler rules solely in this file. Keep
permissions in `robots.txt` and page/HTTP robots metadata.

## 5. humans.txt

**Purpose:** Publish concise project ownership, source, technology, and credit
information for people and simple tooling.

**Implementation:** `/humans.txt` identifies Shipyard, its maintainer,
contributors, source repository, canonical domain, purpose, framework, and
metadata review date.

**Why it matters:** It improves transparency without adding UI or executable
code.

**AI impact:** Offers supplementary provenance signals; no crawler support is
assumed.

**SEO impact:** Neutral.

**Browser impact:** Human-readable plain text.

**Maintenance notes:** Refresh the review date and stack only when facts change.
Do not publish private contact details.

## 6. .well-known/security.txt

**Purpose:** Give security researchers a standards-based private reporting path.

**Implementation:** `/.well-known/security.txt` follows RFC 9116 with required
`Contact` and `Expires` fields plus `Preferred-Languages`, `Canonical`, and
`Policy`. `SECURITY.md` supplies the referenced disclosure policy. HTTP metadata
sets `text/plain; charset=utf-8`.

**Why it matters:** Researchers can locate a responsible disclosure channel
without opening a public issue.

**AI impact:** Security agents and scanners can parse a standard contact record.

**SEO impact:** Neutral; the resource is operational metadata.

**Browser impact:** Directly readable over HTTPS.

**Maintenance notes:** Renew the expiry before 2027-07-01. Confirm that GitHub
private vulnerability reporting remains available and that the canonical URL
continues to return HTTP 200 without a cross-domain redirect.

Reference: [RFC 9116](https://www.rfc-editor.org/rfc/rfc9116.html)

## 7. RSS feed

**Purpose:** Expose chronological product updates to feed readers and
machine-consumption workflows.

**Implementation:** `/feed.xml` returns RSS 2.0 with an Atom self-link,
canonical links, stable GUIDs, RFC 822 dates, UTF-8 content type, and cache
metadata. Entries reflect actual shipped product milestones.

**Why it matters:** RSS provides a durable, open update channel without adding a
blog or changing UI.

**AI impact:** Agents can monitor factual product changes through a structured
feed.

**SEO impact:** Feeds do not directly improve ranking but can improve
discoverability and syndication.

**Browser impact:** Browsers and feed readers receive valid XML; the root
metadata advertises the feed.

**Maintenance notes:** Add entries only for shipped, public changes. Keep GUIDs
stable and dates accurate. Validate after each update with an RSS validator.

## 8. manifest.webmanifest review

**Purpose:** Describe Shipyard to browsers as an installable web application.

**Implementation:** `/manifest.webmanifest` defines name, short name,
description, start URL, scope, standalone display, language, categories, dark
theme colors, and the existing scalable SVG icon.

**Why it matters:** It gives browsers consistent app identity and install
metadata.

**AI impact:** Small provenance benefit through explicit app naming and purpose.

**SEO impact:** Minimal direct impact; it supports overall technical quality.

**Browser impact:** Enables consistent installation metadata and theme color
without changing the rendered application.

**Maintenance notes:** Keep name, description, colors, start URL, and icon paths
stable. Add raster maskable icons only after approved brand assets exist.

## 9. Favicon verification

**Purpose:** Provide a stable, recognizable site icon to browsers and search
results.

**Implementation:** `app/icon.svg` is square, scalable, same-origin, and
explicitly declared in root metadata and the web app manifest.

**Why it matters:** Consistent favicon discovery strengthens brand recognition
and avoids browser fallbacks.

**AI impact:** Minor entity-identification benefit.

**SEO impact:** Google may display the favicon in search results when its
guidelines are met; appearance is not guaranteed.

**Browser impact:** Tabs, bookmarks, shortcuts, and installed-app metadata can
reuse the same stable asset.

**Maintenance notes:** Keep the URL stable and crawlable. If raster icons are
introduced, use square assets at least 48×48 and include an approved
apple-touch icon.

Reference: [Google favicon guidance](https://developers.google.com/search/docs/appearance/favicon-in-search)

## 10. Open Graph verification

**Purpose:** Control how canonical Shipyard pages appear when shared.

**Implementation:** Root and route metadata include page-specific title,
description, canonical URL, site name, locale, type, and a 1200×630 image with
descriptive alternative text.

**Why it matters:** Deterministic share metadata avoids generic or misleading
previews.

**AI impact:** Open Graph values provide concise page identity to parsers that
consume social metadata.

**SEO impact:** Open Graph is not a direct Google ranking mechanism, although
Google may use `og:title` among several title-link signals.

**Browser impact:** Social and messaging clients can render rich link previews.

**Maintenance notes:** Keep metadata aligned with visible page content. Test
deployed URLs with platform share debuggers after material copy changes.

## 11. Twitter Cards verification

**Purpose:** Provide an explicit large-image card for X/Twitter-compatible
parsers.

**Implementation:** Every metadata-enabled public route emits
`summary_large_image`, page-specific title and description, and the generated
1200×630 Twitter image.

**Why it matters:** Prevents reliance on incomplete Open Graph fallback behavior.

**AI impact:** Supplies another concise metadata representation.

**SEO impact:** No direct ranking impact.

**Browser impact:** Rich previews in compatible clients.

**Maintenance notes:** No creator/site handle is declared because no verified
official account was supplied. Add one only after ownership is confirmed.

## 12. Canonical verification

**Purpose:** Consolidate duplicate URLs and declare the preferred production
address for each indexable page.

**Implementation:** Canonicals use the fixed HTTPS apex
`https://genshipyard.com`. Query-driven tools canonicalize to their base route.
Dynamic builder and contract pages canonicalize to their encoded path. The
skills subdomain continues to redirect or rewrite through existing middleware,
while metadata points to the apex.

**Why it matters:** It reduces duplicate indexing from query strings, Vercel
deployment hosts, and alternate hostnames.

**AI impact:** Retrieval systems receive a stable citation target.

**SEO impact:** Canonicals and sitemap entries agree, strengthening the preferred
URL signal.

**Browser impact:** None; canonical links are document metadata.

**Maintenance notes:** Preserve the production host in
`lib/metadata/site.ts`. Never canonicalize every route to the home page.

Reference: [Google canonical guidance](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls)

## 13. Structured Data validation

**Purpose:** Describe Shipyard's organization, website, and web application as
connected entities.

**Implementation:** Root JSON-LD contains an `Organization`, `WebSite`, and
`WebApplication` graph with stable `@id` values, canonical URLs, publisher
relationships, operating system, browser requirements, free offer, and factual
feature list.

**Why it matters:** Structured data gives parsers explicit entity relationships
instead of requiring inference from UI text.

**AI impact:** Improves factual extraction and entity reconciliation.

**SEO impact:** The graph is valid schema.org markup. No rating or review was
invented, so Shipyard does not claim eligibility for Google's Software
Application rich result, which requires rating/review data in addition to name
and offer.

**Browser impact:** None; JSON-LD is non-visual.

**Maintenance notes:** Validate deployed markup with Schema Markup Validator and
Google Rich Results Test. Update features and network claims when the product
changes.

References:
[Google structured data policies](https://developers.google.com/search/docs/appearance/structured-data/sd-policies),
[SoftwareApplication guidance](https://developers.google.com/search/docs/appearance/structured-data/software-app)

## 14. Dynamic OG image validation

**Purpose:** Generate consistent social imagery from source-controlled metadata
instead of relying on an external asset pipeline.

**Implementation:** Next.js `ImageResponse` routes generate 1200×630 PNG images
for Open Graph and Twitter Cards using a self-contained layout with no network
font or image dependency.

**Why it matters:** Builds are deterministic, previews remain on-brand, and
external image-host failure is eliminated.

**AI impact:** Image alt text and surrounding metadata reinforce page identity.

**SEO impact:** Better share presentation can improve referral click-through;
there is no direct ranking guarantee.

**Browser impact:** Share clients fetch a normal PNG response.

**Maintenance notes:** Build-test both image routes after Next.js upgrades.
Verify HTTP 200, `image/png`, 1200×630 dimensions, and no redirects on the
production host.

## 15. Search Console verification guidance

**Purpose:** Establish verified ownership and operational monitoring without
committing a private or fabricated token.

**Implementation:** Root metadata conditionally emits Google's verification meta
tag only when `GOOGLE_SITE_VERIFICATION` is configured. The variable is
documented in `.env.local.example`; no value is stored in Git.

**Why it matters:** Verified owners can submit sitemaps, inspect rendered URLs,
request recrawls, and monitor indexing and structured-data issues.

**AI impact:** Indirect; healthy Google indexing supports discovery in Google
Search and its AI search experiences.

**SEO impact:** Verification itself does not improve ranking, but it enables
diagnostics and submission workflows.

**Browser impact:** The verification meta tag is invisible.

**Maintenance notes:**

1. Prefer a Domain property for `genshipyard.com` and verify it with the exact
   DNS TXT record supplied by Search Console.
2. Keep the DNS record after verification.
3. If DNS access is unavailable, set the exact HTML-tag token value as the
   Vercel Production variable `GOOGLE_SITE_VERIFICATION` and redeploy.
4. Submit `https://genshipyard.com/sitemap.xml`.
5. Inspect `/`, `/deploy`, `/templates`, `/registry`, and one dynamic public URL.
6. Monitor Page Indexing, Core Web Vitals, HTTPS, and structured-data reports.

Reference: [Search Console ownership verification](https://support.google.com/webmasters/answer/9008080)

## 16. Lighthouse improvements

**Purpose:** Improve machine-verifiable technical quality within the strict
metadata-only scope.

**Implementation:** Added manifest and theme metadata, stable scalable icon
declarations, deterministic social images, explicit metadata descriptions,
canonical links, crawl controls, RSS discovery, and caching for operational
metadata.

**Why it matters:** These changes address SEO/PWA metadata audits without
touching interactive code or introducing render-blocking resources.

**AI impact:** Faster, predictable metadata responses aid retrieval.

**SEO impact:** Improves technical completeness. Performance scores remain
primarily governed by application JavaScript, wallet libraries, fonts, and
runtime behavior, which were intentionally out of scope.

**Browser impact:** Better install metadata and no additional client-side
JavaScript.

**Maintenance notes:** Run Lighthouse or PageSpeed Insights against production
on mobile and desktop after deployment. Track LCP, INP, CLS, accessibility, SEO,
and best-practice regressions. Do not chase scores by changing application
behavior without a separate reviewed scope.

Reference: [Chrome Lighthouse](https://developer.chrome.com/docs/lighthouse/)

## 17. AI crawler compatibility review

**Purpose:** Ensure public Shipyard content is accessible, attributable, and
machine-comprehensible without inventing a proprietary standard.

**Implementation:** Public pages remain anonymously reachable and server-render
metadata. Robots explicitly permits major search/retrieval crawlers, the
sitemap exposes canonical entry points, JSON-LD describes entities, and
`llms.txt` supplies an optional concise guide. APIs are excluded from crawl
scope.

**Why it matters:** AI visibility starts with reachable, factual, canonical
content. Special text files cannot compensate for blocked pages, thin content,
incorrect metadata, or WAF denial.

**AI impact:** Improves eligibility for retrieval and citation while making no
guarantee about inclusion or ranking.

**SEO impact:** Aligns AI discovery with normal technical SEO rather than
creating conflicting crawler policies.

**Browser impact:** None.

**Maintenance notes:** Periodically verify crawler guidance and published IP
ranges from providers. Do not trust a user-agent string alone at the WAF layer.
Keep search/retrieval bots distinct from model-training bots when policy changes.

References:
[OpenAI publisher guidance](https://help.openai.com/en/articles/12627856-publishers-and-developers-faq),
[Anthropic crawler guidance](https://support.anthropic.com/en/articles/8896518-does-anthropic-crawl-data-from-the-web-and-how-can-site-owners-block-the-crawler),
[Perplexity crawler guidance](https://docs.perplexity.ai/docs/resources/perplexity-crawlers)

## Validation checklist

Run before release:

```bash
npm run lint
npm test
npx tsc --noEmit
npm run build
```

Validate the production responses:

```text
/robots.txt                         text/plain; HTTP 200
/sitemap.xml                        application/xml; HTTP 200
/llms.txt                           text/plain; HTTP 200
/ai.txt                             text/plain; HTTP 200
/humans.txt                         text/plain; HTTP 200
/.well-known/security.txt           text/plain; charset=utf-8; HTTP 200
/feed.xml                           application/rss+xml; charset=utf-8; HTTP 200
/manifest.webmanifest               application/manifest+json; HTTP 200
/icon.svg                           image/svg+xml; HTTP 200
/opengraph-image                    image/png; HTTP 200
/twitter-image                      image/png; HTTP 200
```

For HTML pages, confirm:

- exactly one canonical URL;
- unique title and description;
- Open Graph and Twitter card values;
- public routes are indexable;
- `/admin`, `/history`, and `/handoff` emit `noindex`;
- JSON-LD parses as valid JSON and matches visible product facts.

## Out-of-scope observations

- Search Console ownership and sitemap submission require an authorized account
  or DNS change and cannot be completed safely from source code alone.
- A raster apple-touch icon and maskable PWA icon require approved brand assets.
- Performance work involving fonts, wallet bundles, or component loading would
  affect application delivery and requires a separate UI/build scope.
- Historical or visible legal/product copy was not changed under this
  metadata-only mandate.
